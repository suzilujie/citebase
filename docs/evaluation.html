1. 方法与指标

评测要回答的不是"能不能答"，而是三个可证伪的问题：找得到吗、引用对得上吗、 该拒的时候拒了吗。题集写在 evals/questions.json，随代码版本化；每道题标注期望文档与是否可回答。

指标定义分母为什么需要它
Recall@5 期望文档出现在前 5 个检索块的题目占比 17 条可回答问题 检索不到，后面全是空谈；只看最终答案无法区分"检索差"还是"生成差"
引用命中率 回答中至少一个角标指向期望文档的题目占比 17 条可回答问题 检索到了却没用上，等于没有引用；这项专抓"引用了别的文档"
拒答准确率 判定正确的题目占比：可答题 = 作答且引用命中；不可答题 = 明确拒答 全部 20 条 只统计 3 条不可答题会让分母太小；把"该答却拒答"也算错才公平

5. 分臂消融

同一批 17 条可回答问题，分别只走一个检索臂，观察差异：

检索臂Recall@5MRR解读
仅向量94.1%0.919漏掉 1 题：编号类问题被向量"抹平"
仅关键词100%1.000本题集问法与原文高度重合，关键词臂占优
融合（RRF）100%0.956召回补齐，但排序偶有互换
怎么读这张表。 离线模式的向量臂是"哈希词袋"，本质仍是词面匹配，所以它和关键词臂高度同质， 融合自然拿不到额外收益（MRR 甚至因融合而轻微下降）。这是离线可跑的必然代价，不是 RRF 的问题： 配 EMBED_PROVIDER=openai 后向量臂变成真语义向量，才能在"问法完全不同"的问题上体现价值。 报告这组数字，比只报一个 100% 更诚实，也更能说明系统的能力边界在哪。

6. 失败分析

6.1 第一轮：拒答准确率 85%，三条不可答题全被"答"了

首轮结果为 recall@5 100% / 引用命中 100% / 拒答准确率 85%，三条失败均为不可答题：

题目系统当时的回答（片段）根因
q18 股票期权 「本手册适用于星澜科技有限公司全体正式员工…」 [2]「公司实行弹性上班制度…」 问题里的「公司/员工」在几乎每个块都出现，被当成命中的证据
q19 2025 营业收入 「公司系统统一启用双因素认证。」 [1]「星澜科技员工手册（2025 修订版）」 只有年份「2025」匹配上，数字被当成有效重合
q20 gym memberships 「Interest is paid only when the delay is caused by the company…」 “company” 是唯一的共同词，属于英文停用词

6.2 根因：抽取式缺少"证据门槛"

原实现只要句子里出现任意一个查询词就给分。向量检索永远返回 8 条最近邻，于是"有上下文"被误判成"有依据"。 归一化（除以句长、除以词数）只能调整排序，无法改变"0 个有效证据 vs 1 个弱证据"都被当作命中的事实。

6.3 修复：通用词不计分 + 双词命中

  • 维护一份通用词表（公司、员工、制度、多少、哪些 / the、company、policy…）与纯数字降权规则，它们永不构成证据。
  • 问题里有 ≥2 个特定词时，某一句必须同时命中 2 个才允许引用；只有一个特定词的问题才降为 1 个。
  • 若过滤后没有特定词，或没有任何句子达标 → 返回空答案，由同一道引用守卫改写为「文档中未提及相关内容。」

6.4 复测

拒答准确率 85% → 100%，三项指标同时为 100%，17 条可回答问题没有出现新的误拒。 这组"失败 → 根因 → 修复 → 复测"的记录本身比数字更有用：它说明指标是能驱动的，而不是摆设。

6.5 另一处修复：PDF 跨行导致的"半句引用"

PDF 提取出的文本按版面宽度硬换行，按行切块会让每个块的起点都落在句子中间，引用面板读起来像被撕开的纸。 修复是在解析阶段重组段落：行尾是句末标点就断段，否则与下一行拼接；章节标题（1. Scope）独立成行。 这项与指标无关，但直接决定"引用是否可读"——而可读性正是这个产品的卖点。

6.6 生成式路径实测（DeepSeek，run #5）

配置 https://api.deepseek.com/v1 + deepseek-chat 后，同一批 20 题全部走 LLM： 17 条可答题全部给出 1–3 句结论、每条结论都带 [n]，且引用命中期望文档；3 条不可答题全部回复 「文档中未提及相关内容。」，引用数为 0。没有一条被引用守卫改写成拒答，也没有出现越界角标。

观察实际表现说明
角标位置句末，部分落在句号前（[1]。）不影响解析与校验；若要严格排版，可在后处理里把角标移到标点之后
引用数量每题 1–3 个，最多两处不同块提示词要求"每句结论都标来源"，未出现整段无角标
跨文档混淆无中英文问题都指向了正确文档：中文题引 policy/handbook，英文题引 invoice-guide.pdf
回答语言英文问题也答中文提示词约束为简体中文；若面向海外可改为"跟随问题语言"
耗时0.58–1.12 s / 题含网络往返，20 题约 18 s
一个必须说清的约束。 DeepSeek 只提供对话补全，没有 embeddings 接口，所以 EMBED_PROVIDER 仍为 local（哈希向量）。也就是说 run #5 证明了"生成与引用校验"可用， 但并没有把"语义检索"也一并验证；那需要另接一家 embeddings 服务并 bun run reembed。

7. 局限

局限影响下一步
题集自建、语料仅 3 份指标偏乐观，无法外推引入外部文档（真实合同/制度），并补充"问法完全不同"的改写题
离线向量为词袋语义能力未验证用真实嵌入模型复跑同一题集，对比两个向量臂
不可答题仅 3 条拒答阈值可能过拟合扩充到 10 条以上，包含"部分相关但答案缺失"的难负例
生成式只在 DeepSeek 上验证过其他模型的角标纪律可能更差换模型后重跑 run 并对比"被守卫改写的题数"
回答语言固定为简体中文英文提问会被译成中文作答面向海外客户时改为跟随问题语言

8. 复现

# 1. 起库并导入样例（start.bat 已包含这两步）
docker compose up -d
bun run seed

# 2. 命令行跑分（含分臂消融）
bun run eval

# 3. 通过 API 跑分（服务已启动）
powershell -NoProfile -File tools/eval.ps1

# 4. 单测与静态检查
bun test
bunx biome check src web/src

每次评测写入一行 eval_runs（含逐题明细 jsonb），因此不同时间、不同参数的结果可以直接对比，而不是截图留档。
