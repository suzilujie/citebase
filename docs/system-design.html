CiteBase 系统设计

自托管知识库问答 · 可核查引用 · 离线可演示

v1.0 · 2026-11-01 · 代码：pjc/citebase

1. 目标与边界

目标只有一个：让答案里的每一句都能被点开核对。这不是"再加一个聊天框"，而是把"答得有据" 变成产品结构——数据模型存页码与标题路径、回答格式强制角标、服务端做引用校验、前端把出处当作 一等公民展示。顺带解决第二个问题：答不出的时候要承认，而不是生成一段听起来合理的内容。

1.1 范围内

  • PDF / Markdown / TXT 解析、分块、向量化、入库（含内容哈希去重）
  • 向量召回 + 关键词召回，RRF 融合，中文按二元组切分以绕开 Postgres 分词缺陷
  • 生成式（OpenAI 兼容接口）与抽取式（无密钥）两种作答模式，共用同一道引用校验
  • 20 题评测集、三项指标、逐题明细、分臂消融，结果落库可重复对比
  • 单端口交付：Bun 同时托管 API 与构建后的 SPA；Windows 一键 start.bat

1.2 范围外（明确不做）

  • 多租户、组织架构与权限体系（默认单团队自托管，网络边界即权限边界）
  • 扫描件 OCR（只处理带文本层的 PDF，失败时明确报错）
  • 模型微调、rerank 模型、查询改写（都留作后续，见第 11 节）
  • 文档协同编辑与版本管理
  • 托管运维与 SLA 承诺

2. 架构

Browser (React SPA: library / ask / eval)
    │  fetch /api/*
    ▼
Bun + Hono  :15640
    ├── ingest    parse → reflow → chunk → tokenize → embed → store
    ├── retrieve  vector arm ─┐
    │             keyword arm ─┴→ RRF fuse → top CONTEXT_K
    └── answer    llm | extractive → citation guard → refusal
    │
    ├── static    ./public (vite build 产物)
    ▼
Postgres 17 + pgvector  :5440
    documents / chunks(tsvector + vector(384)) / query_logs / eval_runs
    │
    └──(可选) OpenAI 兼容 /chat/completions
为什么只有一个进程。 交付形态要求"起一个容器就能用"。API、静态页、入库、检索、评测都在同一个 Bun 进程里，少一个进程就少一处启动顺序、端口与健康检查问题。代价是无法只水平扩展检索层—— 以本项目量级（万级 chunk）完全不需要。

3. 数据模型

四张表，sql/init.sql 幂等建表，进程启动时再执行一次以兼容旧数据卷。

表关键列作用
documents id, filename, mime, size_bytes, sha256, page_count, chunk_count, status, error 文档清单。状态机 pending → ready | failed；sha256 上唯一索引实现幂等入库。
chunks doc_id, ordinal, page, heading_path, content, char_start, char_end, search_text, tokens, embedding 检索与引用单元。page/heading_path 让引用可定位；search_text 存分词结果。
query_logs question, mode, retrieved_ids[], cited_ids[], latency_ms 每次提问都留痕。召回集与引用集分开记，两者的差异就是"检索到了但没用上"或"用了没检索到"。
eval_runs recall_at_5, citation_hit, refusal_acc, total, detail jsonb 一次评测一行，逐题明细进 jsonb，前端直接读表展示。

索引

chunks_embedding_idx  hnsw (embedding vector_cosine_ops)   -- 无需训练集，灌数据即可用
chunks_tokens_idx     gin  (tokens)                        -- 关键词臂
chunks_doc_idx        btree (doc_id, ordinal)               -- 重建文档原文
documents_sha_idx     unique (sha256)                       -- 去重
为什么不用 IVFFlat。 IVFFlat 需要先用数据训练聚类中心，空表导入时质量不可控；HNSW 写入即生效， 代价是索引更大、构建更慢，在万级数据量下都不是问题。

4. 入库流水线

  1. hash：sha256(bytes)，命中 status=ready 的既有文档直接返回原记录（duplicate: true），不重复消耗 embedding。
  2. parse：PDF 用 unpdf 按页取文（mergePages: false，页码天然正确）；Markdown 按标题切成"节"，每节记为 page 1 且带标题路径；TXT 整篇一页。
  3. reflow：PDF 文本是按版面硬换行的，直接把行当段落会让每个 chunk 都从句中开始。按"行尾是否为句末标点"重组段落。
  4. chunk：先按空行切段，超长段再按句末标点切；CHUNK_SIZE=700 打包，CHUNK_OVERLAP=120 把上一块尾部带入下一块，且不跨页合并（否则页码会撒谎）。
  5. tokenize：中文按二元组切分、英文按小写词切分，空格连接后同时写入 search_text 并生成 tokens。
  6. embed：local 模式为确定性哈希向量（词袋），openai 模式调用兼容接口；两种模式都做 L2 归一化。
  7. store：单事务写入 chunk（每批 40 行多值 insert），随后回填 chunk_count/page_count 并置 ready。
失败必须可见。 解析或向量化抛错时写 status=failed + error，接口返回 422 而不是 500， 前端列表标红并显示原因。宁可让用户看到"这份 PDF 没有文本层"，也不要静默收录一个空文档。

5. 混合检索

5.1 两路召回

臂SQL 要点擅长短板
向量 order by embedding <=> $1 limit TOP_K 同义改写、问法与原文措辞不同 编号、错误码、金额这类精确串会被"抹平"
关键词 tokens @@ to_tsquery('simple', …) + ts_rank_cd 精确串、"只出现一次"的专有名词 问法不同就完全匹配不上

5.2 中文分词：Postgres 默认分词器会把整段中文当成一个词

to_tsvector('simple','报销流程') 只产生一个 lexeme，搜「报销」召回为零。 不装 zhparser（要编译扩展，交付环境不可控）的替代方案：两侧都自己切。 入库时把中文切成重叠二元组存进 search_text，查询串走同一个函数： 

报销流程  →  报销 销流 流程        （入库）
搜索「报销」→  报销                （查询，必然命中）

查询侧把词项按出现次数排序取前 24 个，用 | 连接成 OR 查询——单个罕见二元组不该让整条查询归零。

5.3 RRF 融合

score(d) = Σ over arms   1 / (RRF_K + rank(d)),   RRF_K = 60

余弦相似度与 ts_rank_cd 不在同一量纲上，直接相加需要标定，而标定值会随语料漂移。 RRF 只看排名，天然免疫这件事；k=60 把头部排名的差距压平，使"两路都认为相关"比"一路极自信"更重要。 融合后取 CONTEXT_K=8 作为上下文。

6. 作答与引用守卫

6.1 两种模式，一道闸门

模式触发条件产出
llm ANSWER_MODE=auto 且存在 API Key 2–4 句中文结论，每句带 [n]；温度 0.1；失败自动降级（已用 deepseek-chat 实测：0.6–1.1 s/题）
extractive 无 Key，或显式配置 按查询词重合度挑原句并附角标，零幻觉

抽取式不是"降级凑数"，它是离线演示的交付底线：客户拿到仓库第一件事是双击 start.bat， 不能要求他先申请密钥。为此它必须有真正的拒答能力——见下。

6.2 引用守卫（两种模式共用）

  1. 越界剔除：[9] 在只给了 8 条上下文时必然被删掉，读者看不到死链。
  2. 零引用改写：有效角标为 0 → 整段替换为「文档中未提及相关内容。」，并清空出处面板。
  3. 落库对账：retrieved_ids 与 cited_ids 同时写入 query_logs，便于事后判断是检索问题还是生成问题。

6.3 抽取式如何避免"什么都敢答"

向量检索永远会返回 8 条最近邻，所以"有上下文"不等于"有依据"。抽取式加了两道词法门槛：

  • 通用词不计分：公司 / 员工 / 制度 / 多少 / the / company 这类词几乎每块都有，匹配上不构成证据；纯数字也降权。
  • 至少两个特定词命中（问题足够长时）：一个 chunk 的某一句必须同时命中两个非通用查询词才允许被引用。

实测效果直接体现在评测上：第一版没有这两道门槛，3 条不可回答问题全部被"答"了（拒答准确率 85%）； 加上之后复测为 100%，且 17 条可回答问题仍然全中。

7. 关键决策

#决策理由代价 / 何时重估
D1 pgvector + tsvector 同库，不引专用向量库 "起一个容器就能用"；少一个组件就少一处失败点 向量检索性能不及专用库；>百万 chunk 或需多副本时再评估
D2 关键词臂 + RRF，而非纯向量 编号、合同号、错误码靠向量容易失灵 多一次查询与融合成本（毫秒级）
D3 默认离线可跑（哈希向量 + 抽取式） 交付的分水岭：没有 Key 也必须能演示 离线向量本质是词袋，语义能力需 EMBED_PROVIDER=openai
D4 引用可溯源写进数据模型（page / heading_path / 字符偏移） 没有位置信息的引用等于没引用 分块必须按页，chunk 不能跨页合并
D5 评测集先行，题集随代码版本化 把"能答"变成"可证明答对" 自建题集有偏；需扩充外部题与负例
D6 前端不引组件库，Tailwind 手写四类基础组件 UI 只有卡片/按钮/输入/角标，依赖树越小交付越稳 无障碍细节需自行补齐，已在 README 标注

8. 接口

方法路径说明
GET/api/health数据库连通性、当前回答模式、向量提供方与维度
GET/api/documents文档列表 + 文档数/块数统计
POST/api/documentsmultipart 上传（字段名 file）；超限 413，解析失败 422，重复 200 + duplicate:true

POST/api/query提出问题，返回 answer / mode / citations / retrievedIds / citedIds / latencyMs
GET/api/query/recent最近 12 次提问（排障用）
GET/api/eval/questions当前题集
POST/api/eval/run同步跑完 20 题并落库
GET/api/eval/latest最近一次评测（含逐题明细）

未知 /api/* 返回 JSON 404，其余路径回落到 public/index.html——单端口部署下刷新前端路由不会 404。

9. 前端结构

三个视图，一个目标：让"可核查"成为视觉语言，而不是靠装饰。

  • 文档库：拖拽上传区 + 文档表（类型/页数/块数/状态点）。失败行左侧 3px 红条并显示错误摘要。
  • 问答：左栏对话流，右栏出处面板（≤1080px 折叠到答案下方）。答案中的 [n] 是按钮：点击高亮对应出处并滚动到可视区；出处头部可打开原文。
  • 评测：三张指标卡 + 逐题明细表（PASS/FAIL、期望文档、实际召回文档、耗时），一键重跑。

配色为低饱和深色底 + 单一靛蓝强调色，引用片段一律等宽字体：等宽 = 原文，无衬线 = 系统生成， 用户不读图例也能分辨哪句是文档原话。未配置密钥时顶部显示一条细横条说明当前为抽取式，不弹窗打断。

10. 性能与容量

环节实测 / 预期说明
入库2–5 s / 千块（本地向量）解析 + 分块 + 向量 + 单事务写入；上传在请求内同步完成
检索< 10 ms（17 块语料）两路各 limit 30，HNSW + GIN；语料增长后主要成本在 HNSW 遍历
抽取式作答0–3 ms纯词法打分，无网络
生成式作答0.8–3 s取决于模型服务；45 s 超时后降级为抽取式
评测约 1 s / 20 题抽取式模式下为本地计算；串行执行以保证单题耗时可解释

pg.Pool 上限 8 连接，前端上传串行（并发上传只会争用同一个池，并把内存打满）。 单文件上限 20 MB，bodyLimit 在路由层拦截并返回可读错误。

11. 已知限制与风险

限制影响缓解 / 后续
离线向量是哈希词袋，不是语义模型 无密钥时向量臂≈词面匹配，同义改写命中率低 配 EMBED_PROVIDER=openai 即切换为真语义向量；切换后必须 bun run reembed
换向量模型 = 全量重算 不同模型/维度不可比，混用会得到无意义的相似度 提供 bun run reembed；README 与 .env 注释均写明
无 OCR 扫描件入库直接失败 失败态写明原因；OCR 属独立能力，不塞进本期
评测集自建、语料仅 3 份 100% 是上限值，不代表生产召回 评测页与文档同时标注；分臂消融用于说明趋势而非绝对值
无 rerank / 查询改写 多跳问题、模糊指代效果有限 下一步：cross-encoder rerank、问题改写、按文档过滤
单进程、无鉴权 只适合内网自托管 部署在反向代理后；需要鉴权时在网关层加
